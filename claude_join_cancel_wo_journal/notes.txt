'An order whose Add arrives before its ack is now registered at the ack, using the book and NBBO as they are then, and no book update pays anything for it.' explain

That sentence covers three things.

1. Which orders it applies to. Two messages tell the host about one of our orders:

the feed’s Add, which puts the order in the book under its exchange order ID;
the order gateway’s ack, which tells the host that this ID is ours.

If the ack arrives first, the host knows the ID when the Add shows up and calls on_place at the Add, exactly as before. If the Add arrives first, the host can’t yet tell the order is ours. The book applies it like any other order, the cancel tactic doesn’t track it, and any of our orders behind it count it as a market round lot.

2. “Registered at the ack, using the book and NBBO as they are then.” When the ack arrives, the host looks the ID up in its order table, where the Add already stored the order’s queue handle. It then calls on_place_late(id, sym, side, px, t_add, qh, cb), and from then on the order is tracked like any other. What on_place would have taken at the Add is taken from the current state instead:

(a) uses the orders and shares ahead now.
(b) uses the round lots ahead now, with zero cancellations, and counts cancellations from now on.
(c) measures “moved away” from the NBBO now.
(d) starts from the join signal’s count if that signal is still live, otherwise from 0.

Nothing that happened between the Add and the ack is seen:

feed:     Add(id 7)   R1 cancels   exec above us   NBBO moves         R2 cancels
gateway:                                                     ack(id 7)
tactic:   market      not seen     not seen*       not seen  on_place_late   counted
          order

* seen only if the join signal was live, through its tape.

So R1’s cancellation never counts toward (b), and that NBBO move never counts toward (c). For (d), executions in that window count only through the join signal. One more consequence: an order at the front of the queue at its ack has nothing ahead to count, so (b) never fires for it.

3. “No book update pays anything for it.” The journal version aimed to rebuild the state as it was at the Add. To do that, every update of a tracked symbol wrote a 32-byte entry into a shared ring, in case some order there later turned out to be ours. That cost 0–6 TSC on every message, even when no order was ever late.

Now nothing is recorded in advance. The handler’s machine code is identical to the journal version built with the journal compiled out. The only cost is inside on_place_late: 66–82 TSC against 56–64 for on_place, paid once per late order, when its ack arrives.

The trade: you get the per-message cost back, and give up exactness for orders whose ack comes after the Add. The loss is mostly (b) and (c) decisions that would have fired before the ack. In the stress test, 31% of those orders had been decided before the ack. For orders not yet decided at the ack, 91% got the same first decision on the same update. Yes, four ideas, largest payoff first. The first two remove real work from the hot path; the last two mostly remove code and test surface.

1. Count instead of reading the queue for (a) and (b). Our order always joins the back of its level. Without size-up priority, the orders ahead of it can only shrink or leave. So everything (a) and (b) need can be set once at placement and then updated from each event:

At placement: orders ahead, shares ahead and round lots ahead come straight from the level’s order count, total shares and a round-lot count, minus our own orders.
On each removal or cut at our price: the host passes the order’s Add sequence number and its size before and after. It already has the order-table entry in hand when it applies the update. A lower sequence than ours means the order was ahead, so the tactic adjusts that order’s counters and counts any cancellation.
(a) compares the counters against N and K. (b)’s “at the front or only odd lots ahead” becomes “no round lots left ahead”, and the ratio is cancellations over n0.

What it removes:

the placement walk: 58–60 TSC up to 16 orders ahead, about 2,200 behind 1,024;
counting the orders ahead on each removal at an armed price: 14–16 TSC;
the look-ahead once the ratio is met: up to about 96 TSC;
the per-order flags in QBlockList.

The tactic would no longer read the host’s queue at all, so the host could keep its book in any structure.

What it costs:

The host passes sequence and sizes instead of qflags, and keeps a round-lot count per level.
An order registered at its ack needs a count of what is ahead of it at that moment, which means one walk at the ack.

It should give the same decisions as today. The brute-force models in the test would confirm that.

2. Drop the adaptive volatility term in (c). Replace σ√horizon with a per-symbol depth threshold that the strategy sets and can change at any time.

What it removes:

the σ and τ updates on every update of a tracked symbol;
pinning (set_tracking exists mainly to keep those estimates warm);
four parameters;
the venue-volatility build and its hook.

A pinned symbol with no orders costs 12 / 34 / 20 TSC today (NBBO unchanged / moved / execution), against 8–10 untracked. I believe most of the extra on NBBO moves and executions is that bookkeeping, and symbols with orders pay it too. I can measure the exact share.

The cost: the threshold no longer widens on its own in a fast market.
